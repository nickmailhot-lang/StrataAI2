# Explicit local attachment release fixture

The sanctioned private local object-storage adapter can now be selected by an explicit `STRATAAI_ATTACHMENT_TEST_LOCAL_ROOT` absolute path only when the actual host environment and `ASPNETCORE_ENVIRONMENT` are IntegrationTest. API/Worker startup supplies the real host environment separately; a configuration value cannot override that proof. If `DOTNET_ENVIRONMENT` is supplied, it must also be IntegrationTest. Storage must be explicitly enabled, and the application still uses its Production runtime descriptor and restricted PostgreSQL stores. Demo activation remains forbidden. This is a test capability, never fallback after S3 failure.

Without that setting, enabled runtime storage still requires the canonical managed AWS bucket, owner and region, regional HTTPS endpoint, SDK credentials and current private bucket checks. No custom endpoint or new Production provider was added. Startup resolves the selected storage adapter behind fixed diagnostic refusal. Local fixture readiness rechecks private directory permissions and links as well as PostgreSQL and, on the Worker, its existing local scanner socket. The directory must be operator-owned; the existing local adapter does not independently attest its Unix owner.

Upload policies, source admission, durable scan jobs, the separate Worker's ClamAV protocol, isolated image decoder, committed preview publication, original receipt recovery and integrity-checked delivery are unchanged. The same release images can use a disposable private directory and scanner protocol fixture to exercise the entire pipeline. Such a run will prove application pipeline behavior with explicitly declared providers; it will not prove managed AWS availability or a real malware engine if its scanner replies are simulated.

Domain configuration boundary tests and mandatory exact-image refusal cases reject Production/Development activation, conflicting host environments and relative roots. The argument verifier now covers all 23 refusal cases, including the six added host/root cases; it passes locally. That is argument construction evidence, not executed image startup proof.

The mandatory container workflow now runs `test-attachment-image-pipeline.sh`. It creates disposable actors and a scoped Organization, switches the exact API/Worker images to the explicitly selected private local directory, and supplies the declared clamd protocol simulator. It uploads a valid PNG with private trailing metadata, waits for the real Worker scan/isolated decoder/committed publication to expose the candidate, selects Board ownership, checks sanitized bytes, copies to a private Board with a new image identity, archives the source and checks copied-byte survival and anonymous denial. Cleanup restores the normal release/auth configuration and removes only its verified disposable directory. No source application response or publication record is patched into existence by this fixture.

The lifecycle extension archives the original attachment through HTTP, then recovers the byte-identical original Board selection acknowledgment using its original key and proves owned preview survival. It also makes the independent copied Board PUBLIC, verifies anonymous PNG bytes, narrows it to PRIVATE and verifies refusal, then clears its selection and verifies refusal even for the owner. All are assertions in the mandatory scenario; execution is still pending.

The initial delivered image must have a PNG signature and terminal IEND record, a nonzero owned image reference, fixed safe filename, no-store/private caching, nosniff, sandbox policy, no ranges, no redirect and no ETag. These checks run through the release web proxy, alongside removal of the original private trailing metadata. They are not completed proof until the container scenario succeeds.

The same live fixture now runs an explicit Playwright configuration at 1280px and 390px before its HTTP lifecycle assertions. Browser dependencies are installed before this mandatory stage. The browser authenticates the disposable actor, reviews the genuinely published Card candidate, selects through the real API, drops only the first already-committed response, retries the original command, renders the real private PNG and creates/navigates to an independent image-backed private Board copy. It checks focus, competing-write fences, overflow and axe violations. No application response, PNG bytes or publication metadata is simulated in these scenarios. Only the scanner verdict provider remains the declared simulator. Browser typecheck and collection pass; executed native proof is pending.

The alternate `.case.ts` file is excluded from ordinary `.spec.ts` discovery and is run explicitly by the mandatory pipeline script with a private fixture input file. This avoids ordinary scenarios accidentally relying on a provider configuration that has already been withdrawn. The API/web are recreated together when entering/restoring the fixture so the release proxy resolves the current API process. HTTP assertions read the actual Board revision after native selections; the reviewed revision is never assumed to remain at its initial value.

Shell/Python syntax and argument checks pass locally. This Windows Python build lacks Unix sockets, so simulator PING/framed-stream/counter execution was unavailable locally; the mandatory Linux source job now runs that check. Full Docker pipeline execution also remains pending Linux CI; Windows has no local Docker runtime. This scenario uses local private storage and a scanner protocol simulator, so it does not prove managed AWS behavior or malware-engine accuracy. Native rendering, remaining lifecycle/concurrency/performance and full ticket acceptance still require separate evidence. Do not close PRD-04/PRD-14/ARCH-07 on this unexecuted scenario.
