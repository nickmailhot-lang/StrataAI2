PRD Identifier\n**PRD-18**\n\n## 2. Feature Name\n**Archiving, Restoration, Permanent Deletion and Audit Integrity**\n\n## 3. Executive Summary\nDefines ACTIVE/ARCHIVED/DELETED lifecycle semantics, archive browser, restoration, permanent deletion safeguards, and audit preservation.\n\n## 4. Problem Statement\nA Trello-class collaborative Kanban product appears simple at the surface but depends on precise domain rules, authorization, lifecycle semantics, concurrency controls, and predictable interaction behavior. This PRD defines the behavior required for **Archiving, Restoration, Permanent Deletion and Audit Integrity** without relying on proprietary implementation details.\n\n## 5. Product Objective\nDeliver a testable, production-oriented implementation of this domain that integrates consistently with the canonical Organization → Board → List → Card model.\n\n## 6. User Personas\n- **Organization Owner/Admin** — governs membership and organization-level configuration.\n- **Board Admin** — manages board-level collaboration and controls.\n- **Contributor** — creates and changes work items.\n- **Viewer** — inspects content without mutation rights.\n- **Public Visitor** — may inspect PUBLIC boards only where permitted.\n\n## 7. User Stories\n- As a user, I can archive instead of accidentally deleting work.\n- As a user, I can browse archived cards/lists.\n- As a user, I can restore archived work.\n- As a user, I can permanently delete only after confirmation.\n\n## 8. Functional Requirements\n- **LIFE-FR-001** — Lifecycle-aware entities SHALL support ACTIVE, ARCHIVED, DELETED or an equivalent explicit state model.\n- **LIFE-FR-002** — Archive SHALL be reversible and distinct from permanent deletion.\n- **LIFE-FR-003** — Archived cards/lists SHALL be hidden from the normal board canvas.\n- **LIFE-FR-004** — Provide an Archived Items interface for authorized users.\n- **LIFE-FR-005** — Archived cards/lists SHALL be restorable when their parent context permits.\n- **LIFE-FR-006** — Permanent deletion SHALL require archived state.\n- **LIFE-FR-007** — Permanent deletion SHALL require explicit confirmation and server-side authorization.\n- **LIFE-FR-008** — Deletion confirmations SHALL state irreversibility.\n- **LIFE-FR-009** — Deleting a list containing cards SHALL explicitly disclose cascading impact.\n- **LIFE-FR-010** — Audit/activity integrity SHALL survive ordinary archive and account removal.\n- **LIFE-FR-011** — Search and notification surfaces SHALL not expose deleted content.\n- **LIFE-FR-012** — Data-retention implementation SHALL distinguish product deletion from low-level backup-retention windows.\n\n## 9. Detailed Interaction Behaviour\n- Changes should appear immediately using optimistic updates when rollback/reconciliation is safe.\n- The server is authoritative for authorization, validation, version, and persisted state.\n- Shared-state changes emit domain events and become visible to other authorized clients through the realtime layer.\n- Destructive operations follow PRD-18 lifecycle rules.\n- Controls unavailable to the user may be hidden/disabled for UX, but the same action must still be rejected server-side.\n\n## 10. Business Rules\n- Archive timestamps retained.\n- Deleted records may be tombstoned or hard-deleted according to security/retention design, but product behavior is irreversible.\n- Restoration cannot violate parent lifecycle state.\n\n## 11. Permission Rules\n- `VIEW`: depends on board/organization visibility and membership.\n- `CREATE`: requires authenticated membership and the relevant create permission.\n- `EDIT`: requires edit rights to the entity's board.\n- `MOVE`: requires edit/move rights in both source and destination contexts where applicable.\n- `COMMENT`: requires authenticated board participation unless future policy explicitly allows otherwise.\n- `INVITE`: requires board/organization administrative rights.\n- `ARCHIVE` / `RESTORE`: require edit or administrative rights according to entity policy.\n- `DELETE`: requires elevated permission and lifecycle preconditions.\n- `ADMINISTER`: limited to the relevant admin/owner role.\n- Every permission is enforced on the server; UI state is never the security boundary.\n\n## 12. Data Requirements\nlifecycleState, archivedAt, deletedAt, deletedBy across Board/List/Card; immutable ActivityEvent retained per policy.\n\nAll mutable records require `createdAt` and `updatedAt`. Concurrency-sensitive records require a version/revision field. Foreign-key or equivalent integrity checks must prevent cross-board/cross-organization inconsistencies.\n\n## 13. API Requirements\nGET /boards/{id}/archive; POST /{entity}/{id}/archive; POST /{entity}/{id}/restore; DELETE /{entity}/{id}\n\nGeneral API rules:\n- Schema-validate all input.\n- Return consistent error envelopes.\n- Enforce authorization before protected disclosure.\n- Support idempotency for retry-prone mutations.\n- Use cursor pagination for unbounded collections.\n- Return updated entity version after successful concurrency-sensitive mutations.\n\n## 14. Real-Time / Event Requirements\nThe following events are directly relevant:\n- `*_ARCHIVED`\n- `*_RESTORED`\n- `*_DELETED`\n\nEvents must contain `eventId`, `eventType`, `actorId`, `organizationId`, `boardId`, `entityType`, `entityId`, `version` where relevant, `metadata`, and `createdAt`. Clients deduplicate by `eventId`.\n\n## 15. UX Requirements\n- Primary desktop interactions must remain fast and visually direct.\n- All critical actions remain available on tablet and mobile web.\n- Destructive actions require explicit confirmation.\n- Empty/loading/error states must not shift the user into ambiguous contexts.\n- The UI should preserve board scroll/list context when opening and closing card detail.\n\n## 16. Accessibility Requirements\n- Target WCAG 2.2 AA.\n- All interactive controls require accessible names.\n- Visible keyboard focus is mandatory.\n- Pointer drag/drop has keyboard equivalent where movement is involved.\n- Dialogs manage focus correctly.\n- Color is never the sole status indicator.\n- Realtime changes that affect the current operation use non-disruptive accessible announcements.\n\n## 17. Error and Empty States\n- Empty state: explain the next permitted action.\n- Permission denied: state that access/action is unavailable without leaking protected metadata.\n- Validation error: identify the affected field/action.\n- Network timeout: preserve recoverable client state and offer retry.\n- Conflict: reconcile to server state and explain that the item changed elsewhere.\n- Deleted/missing entity: distinguish not-found from inaccessible only where doing so is safe.\n\n## 18. Edge Cases\n- Concurrent edits from multiple authorized clients.\n- User loses permission while the entity is open.\n- Parent board/list becomes archived during editing.\n- Duplicate client submission after timeout.\n- Realtime event arrives before mutation response.\n- Realtime event is missed during disconnect and recovered later.\n- Entity is moved while another user is viewing its detail.\n- Very large boards requiring virtualization.\n\n## 19. Non-Functional Requirements\n- Board initial usable rendering target: **<1.5 s** under documented normal conditions.\n- Simple movement visual feedback target: **<100 ms**.\n- Server mutation acknowledgement target: **p95 <500 ms**.\n- Cached card-detail opening target: **<200 ms**.\n- Design supports at least **200 lists/board**, **5,000 cards/board**, and **100,000 archived cards/organization**.\n- Log errors with correlation IDs but avoid logging sensitive content bodies by default.\n\n## 20. Analytics / Telemetry\nTrack:\n- feature open/use counts;\n- mutation latency and success/failure;\n- permission denials by stable error code;\n- realtime reconnect/conflict rates;\n- client exceptions;\n- user-visible retry events.\nDo not use analytics events as the source of truth for audit history.\n\n## 21. Dependencies\n- PRD-04\n- PRD-07\n- PRD-08\n- PRD-15\n- PRD-24\n\n## 22. Out of Scope\nLegal hold/eDiscovery enterprise tooling.\n\n## 23. Acceptance Criteria\n**AC-LIFE-18-01**\nGIVEN an authorized user is using this feature\nWHEN the user performs the primary supported action associated with LIFE-FR-001\nTHEN the server validates authorization and input\nAND the resulting state is persisted\nAND the client reflects the authoritative result.\n\n**AC-LIFE-18-02**\nGIVEN the same operation would violate the rule represented by LIFE-FR-003\nWHEN the user or client attempts the operation\nTHEN the server rejects it with a stable error code\nAND protected state is unchanged\nAND no unauthorized information is disclosed.\n\n**AC-LIFE-18-03**\nGIVEN two clients have the same board or entity open\nWHEN a successful mutation relevant to LIFE-FR-012 occurs\nTHEN the initiating client receives confirmation\nAND other authorized clients receive or recover the updated state without requiring a full manual reload.\n\n## 24. Test Scenarios\n1. Primary happy path.\n2. Empty-state behavior.\n3. Invalid input.\n4. Unauthorized user.\n5. User loses permission mid-session.\n6. Network timeout and retry.\n7. Duplicate request/idempotency.\n8. Two-client concurrent update.\n9. Realtime disconnect/reconnect recovery.\n10. Archived/deleted parent behavior.\n11. Keyboard-only operation.\n12. Mobile viewport.\n13. Large-data performance case where applicable.\n\n## 25. Definition of Done\n- All functional requirements implemented.\n- Server-side authorization tests pass.\n- Schema and migration changes reviewed.\n- Domain events emitted and consumed where required.\n- Unit, integration, and end-to-end tests pass.\n- Accessibility checks and keyboard scenarios pass.\n- Error/empty/loading states are implemented.\n- Telemetry is documented.\n- No known P0/P1 defects.\n- Product behavior is documented sufficiently that another team does not need to invent missing core rules.\n\n## 26.
