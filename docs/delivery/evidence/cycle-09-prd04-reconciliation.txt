PRD Identifier\n**PRD-04**\n\n## 2. Feature Name\n**Board Creation and Board Management**\n\n## 3. Executive Summary\nDefines board lifecycle, metadata, backgrounds, starring, duplication, close/reopen, deletion, and board activity access.\n\n## 4. Problem Statement\nA Trello-class collaborative Kanban product appears simple at the surface but depends on precise domain rules, authorization, lifecycle semantics, concurrency controls, and predictable interaction behavior. This PRD defines the behavior required for **Board Creation and Board Management** without relying on proprietary implementation details.\n\n## 5. Product Objective\nDeliver a testable, production-oriented implementation of this domain that integrates consistently with the canonical Organization → Board → List → Card model.\n\n## 6. User Personas\n- **Organization Owner/Admin** — governs membership and organization-level configuration.\n- **Board Admin** — manages board-level collaboration and controls.\n- **Contributor** — creates and changes work items.\n- **Viewer** — inspects content without mutation rights.\n- **Public Visitor** — may inspect PUBLIC boards only where permitted.\n\n## 7. User Stories\n- As a user, I can create and name a board.\n- As a user, I can change board background and description.\n- As a user, I can star a frequently used board.\n- As a user, I can copy, close, reopen, or delete a board.\n\n## 8. Functional Requirements\n- **BOARD-FR-001** — Authorized organization members SHALL be able to create boards.\n- **BOARD-FR-002** — Board fields SHALL include name, description, organizationId, visibility, background, lifecycleState, createdAt, updatedAt.\n- **BOARD-FR-003** — Authorized users SHALL be able to rename a board and edit its description.\n- **BOARD-FR-004** — Boards SHALL support a background selected from an approved built-in set or stored image reference.\n- **BOARD-FR-005** — Users SHALL be able to star/unstar boards independently.\n- **BOARD-FR-006** — Authorized users SHALL be able to copy a board.\n- **BOARD-FR-007** — Board copy SHALL define whether lists/cards/labels/members are included; default MVP copies structure and card content but not membership or activity.\n- **BOARD-FR-008** — Authorized users SHALL be able to archive/close a board and later reopen it.\n- **BOARD-FR-009** — Permanent board deletion SHALL be available only after archive/close and explicit confirmation.\n- **BOARD-FR-010** — Users SHALL be able to view board activity subject to authorization.\n\n## 9. Detailed Interaction Behaviour\n- Changes should appear immediately using optimistic updates when rollback/reconciliation is safe.\n- The server is authoritative for authorization, validation, version, and persisted state.\n- Shared-state changes emit domain events and become visible to other authorized clients through the realtime layer.\n- Destructive operations follow PRD-18 lifecycle rules.\n- Controls unavailable to the user may be hidden/disabled for UX, but the same action must still be rejected server-side.\n\n## 10. Business Rules\n- Visibility is separate from edit permission.\n- Closing a board is reversible; deletion is irreversible.\n- Board copy creates new entity IDs and no copied audit history.\n\n## 11. Permission Rules\n- `VIEW`: depends on board/organization visibility and membership.\n- `CREATE`: requires authenticated membership and the relevant create permission.\n- `EDIT`: requires edit rights to the entity's board.\n- `MOVE`: requires edit/move rights in both source and destination contexts where applicable.\n- `COMMENT`: requires authenticated board participation unless future policy explicitly allows otherwise.\n- `INVITE`: requires board/organization administrative rights.\n- `ARCHIVE` / `RESTORE`: require edit or administrative rights according to entity policy.\n- `DELETE`: requires elevated permission and lifecycle preconditions.\n- `ADMINISTER`: limited to the relevant admin/owner role.\n- Every permission is enforced on the server; UI state is never the security boundary.\n\n## 12. Data Requirements\nBoard, UserBoardPreference(starred). Index organizationId+lifecycleState. Store background as typed configuration.\n\nAll mutable records require `createdAt` and `updatedAt`. Concurrency-sensitive records require a version/revision field. Foreign-key or equivalent integrity checks must prevent cross-board/cross-organization inconsistencies.\n\n## 13. API Requirements\nPOST /boards; GET/PATCH /boards/{id}; POST /boards/{id}/copy; POST /boards/{id}/archive; POST /boards/{id}/restore; DELETE /boards/{id}; PUT/DELETE /boards/{id}/star\n\nGeneral API rules:\n- Schema-validate all input.\n- Return consistent error envelopes.\n- Enforce authorization before protected disclosure.\n- Support idempotency for retry-prone mutations.\n- Use cursor pagination for unbounded collections.\n- Return updated entity version after successful concurrency-sensitive mutations.\n\n## 14. Real-Time / Event Requirements\nThe following events are directly relevant:\n- `BOARD_CREATED`\n- `BOARD_UPDATED`\n- `BOARD_STARRED`\n- `BOARD_COPIED`\n- `BOARD_ARCHIVED`\n- `BOARD_RESTORED`\n- `BOARD_DELETED`\n\nEvents must contain `eventId`, `eventType`, `actorId`, `organizationId`, `boardId`, `entityType`, `entityId`, `version` where relevant, `metadata`, and `createdAt`. Clients deduplicate by `eventId`.\n\n## 15. UX Requirements\n- Primary desktop interactions must remain fast and visually direct.\n- All critical actions remain available on tablet and mobile web.\n- Destructive actions require explicit confirmation.\n- Empty/loading/error states must not shift the user into ambiguous contexts.\n- The UI should preserve board scroll/list context when opening and closing card detail.\n\n## 16. Accessibility Requirements\n- Target WCAG 2.2 AA.\n- All interactive controls require accessible names.\n- Visible keyboard focus is mandatory.\n- Pointer drag/drop has keyboard equivalent where movement is involved.\n- Dialogs manage focus correctly.\n- Color is never the sole status indicator.\n- Realtime changes that affect the current operation use non-disruptive accessible announcements.\n\n## 17. Error and Empty States\n- Empty state: explain the next permitted action.\n- Permission denied: state that access/action is unavailable without leaking protected metadata.\n- Validation error: identify the affected field/action.\n- Network timeout: preserve recoverable client state and offer retry.\n- Conflict: reconcile to server state and explain that the item changed elsewhere.\n- Deleted/missing entity: distinguish not-found from inaccessible only where doing so is safe.\n\n## 18. Edge Cases\n- Concurrent edits from multiple authorized clients.\n- User loses permission while the entity is open.\n- Parent board/list becomes archived during editing.\n- Duplicate client submission after timeout.\n- Realtime event arrives before mutation response.\n- Realtime event is missed during disconnect and recovered later.\n- Entity is moved while another user is viewing its detail.\n- Very large boards requiring virtualization.\n\n## 19. Non-Functional Requirements\n- Board initial usable rendering target: **<1.5 s** under documented normal conditions.\n- Simple movement visual feedback target: **<100 ms**.\n- Server mutation acknowledgement target: **p95 <500 ms**.\n- Cached card-detail opening target: **<200 ms**.\n- Design supports at least **200 lists/board**, **5,000 cards/board**, and **100,000 archived cards/organization**.\n- Log errors with correlation IDs but avoid logging sensitive content bodies by default.\n\n## 20. Analytics / Telemetry\nTrack:\n- feature open/use counts;\n- mutation latency and success/failure;\n- permission denials by stable error code;\n- realtime reconnect/conflict rates;\n- client exceptions;\n- user-visible retry events.\nDo not use analytics events as the source of truth for audit history.\n\n## 21. Dependencies\n- PRD-03\n- PRD-05\n- PRD-18\n\n## 22. Out of Scope\nAdvanced board views, templates marketplace, Power-Ups.\n\n## 23. Acceptance Criteria\n**AC-BOARD-04-01**\nGIVEN an authorized user is using this feature\nWHEN the user performs the primary supported action associated with BOARD-FR-001\nTHEN the server validates authorization and input\nAND the resulting state is persisted\nAND the client reflects the authoritative result.\n\n**AC-BOARD-04-02**\nGIVEN the same operation would violate the rule represented by BOARD-FR-003\nWHEN the user or client attempts the operation\nTHEN the server rejects it with a stable error code\nAND protected state is unchanged\nAND no unauthorized information is disclosed.\n\n**AC-BOARD-04-03**\nGIVEN two clients have the same board or entity open\nWHEN a successful mutation relevant to BOARD-FR-010 occurs\nTHEN the initiating client receives confirmation\nAND other authorized clients receive or recover the updated state without requiring a full manual reload.\n\n## 24.
