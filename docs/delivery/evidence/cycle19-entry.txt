PRD Identifier\n**PRD-01**\n\n## 2. Feature Name\n**Product Foundation and Information Architecture**\n\n## 3. Executive Summary\nDefines the canonical User → Organization → Board → List → Card hierarchy, application shell, navigation, routing, deep links, responsive behavior, and common entity conventions.\n\n## 4. Problem Statement\nA Trello-class collaborative Kanban product appears simple at the surface but depends on precise domain rules, authorization, lifecycle semantics, concurrency controls, and predictable interaction behavior. This PRD defines the behavior required for **Product Foundation and Information Architecture** without relying on proprietary implementation details.\n\n## 5. Product Objective\nDeliver a testable, production-oriented implementation of this domain that integrates consistently with the canonical Organization → Board → List → Card model.\n\n## 6. User Personas\n- **Organization Owner/Admin** — governs membership and organization-level configuration.\n- **Board Admin** — manages board-level collaboration and controls.\n- **Contributor** — creates and changes work items.\n- **Viewer** — inspects content without mutation rights.\n- **Public Visitor** — may inspect PUBLIC boards only where permitted.\n\n## 7. User Stories\n- As a user, I can navigate among organizations and boards.\n- As a user, I can open a card by deep link without losing board context.\n- As a user, I can understand current organization and board context.\n\n## 8. Functional Requirements\n- **FOUND-FR-001** — The canonical hierarchy SHALL be User → Organization → Board → List → Card.\n- **FOUND-FR-002** — Every Board SHALL belong to exactly one Organization.\n- **FOUND-FR-003** — Every List SHALL belong to exactly one Board.\n- **FOUND-FR-004** — Every Card SHALL belong to exactly one List and exactly one Board.\n- **FOUND-FR-005** — The application SHALL provide global navigation, organization navigation, a board header, board canvas, and card-detail overlay or drawer.\n- **FOUND-FR-006** — Boards and cards SHALL have stable deep-linkable routes using immutable IDs or durable slugs.\n- **FOUND-FR-007** — Opening card details SHALL preserve board context and browser Back behavior.\n- **FOUND-FR-008** — All primary screens SHALL support desktop, tablet, and mobile web.\n- **FOUND-FR-009** — All mutable entities SHALL include createdAt and updatedAt audit timestamps.\n- **FOUND-FR-010** — Entity terminology SHALL be consistent across UI, API, events, persistence, analytics, and tests.\n\n## 9. Detailed Interaction Behaviour\n- Changes should appear immediately using optimistic updates when rollback/reconciliation is safe.\n- The server is authoritative for authorization, validation, version, and persisted state.\n- Shared-state changes emit domain events and become visible to other authorized clients through the realtime layer.\n- Destructive operations follow PRD-18 lifecycle rules.\n- Controls unavailable to the user may be hidden/disabled for UX, but the same action must still be rejected server-side.\n\n## 10. Business Rules\n- A user may access an entity only after server-side authorization.\n- Canonical names may not vary by module.\n- Deep links to archived or deleted objects must resolve to explicit lifecycle-aware states.\n\n## 11. Permission Rules\n- `VIEW`: depends on board/organization visibility and membership.\n- `CREATE`: requires authenticated membership and the relevant create permission.\n- `EDIT`: requires edit rights to the entity's board.\n- `MOVE`: requires edit/move rights in both source and destination contexts where applicable.\n- `COMMENT`: requires authenticated board participation unless future policy explicitly allows otherwise.\n- `INVITE`: requires board/organization administrative rights.\n- `ARCHIVE` / `RESTORE`: require edit or administrative rights according to entity policy.\n- `DELETE`: requires elevated permission and lifecycle preconditions.\n- `ADMINISTER`: limited to the relevant admin/owner role.\n- Every permission is enforced on the server; UI state is never the security boundary.\n\n## 12. Data Requirements\nCore IDs: userId, organizationId, boardId, listId, cardId. Use globally unique identifiers; do not use list/card array index as identity.\n\nAll mutable records require `createdAt` and `updatedAt`. Concurrency-sensitive records require a version/revision field. Foreign-key or equivalent integrity checks must prevent cross-board/cross-organization inconsistencies.\n\n## 13. API Requirements\nGET /organizations; GET /organizations/{id}; GET /boards/{id}; GET /cards/{id}; navigation endpoints may aggregate authorized recent/starred boards.\n\nGeneral API rules:\n- Schema-validate all input.\n- Return consistent error envelopes.\n- Enforce authorization before protected disclosure.\n- Support idempotency for retry-prone mutations.\n- Use cursor pagination for unbounded collections.\n- Return updated entity version after successful concurrency-sensitive mutations.\n\n## 14. Real-Time / Event Requirements\nThe following events are directly relevant:\n- `APPLICATION_CONTEXT_CHANGED`\n- `BOARD_OPENED`\n- `CARD_OPENED`\n\nEvents must contain `eventId`, `eventType`, `actorId`, `organizationId`, `boardId`, `entityType`, `entityId`, `version` where relevant, `metadata`, and `createdAt`. Clients deduplicate by `eventId`.\n\n## 15. UX Requirements\n- Primary desktop interactions must remain fast and visually direct.\n- All critical actions remain available on tablet and mobile web.\n- Destructive actions require explicit confirmation.\n- Empty/loading/error states must not shift the user into ambiguous contexts.\n- The UI should preserve board scroll/list context when opening and closing card detail.\n\n## 16. Accessibility Requirements\n- Target WCAG 2.2 AA.\n- All interactive controls require accessible names.\n- Visible keyboard focus is mandatory.\n- Pointer drag/drop has keyboard equivalent where movement is involved.\n- Dialogs manage focus correctly.\n- Color is never the sole status indicator.\n- Realtime changes that affect the current operation use non-disruptive accessible announcements.\n\n## 17. Error and Empty States\n- Empty state: explain the next permitted action.\n- Permission denied: state that access/action is unavailable without leaking protected metadata.\n- Validation error: identify the affected field/action.\n- Network timeout: preserve recoverable client state and offer retry.\n- Conflict: reconcile to server state and explain that the item changed elsewhere.\n- Deleted/missing entity: distinguish not-found from inaccessible only where doing so is safe.\n\n## 18. Edge Cases\n- Concurrent edits from multiple authorized clients.\n- User loses permission while the entity is open.\n- Parent board/list becomes archived during editing.\n- Duplicate client submission after timeout.\n- Realtime event arrives before mutation response.\n- Realtime event is missed during disconnect and recovered later.\n- Entity is moved while another user is viewing its detail.\n- Very large boards requiring virtualization.\n\n## 19. Non-Functional Requirements\n- Board initial usable rendering target: **<1.5 s** under documented normal conditions.\n- Simple movement visual feedback target: **<100 ms**.\n- Server mutation acknowledgement target: **p95 <500 ms**.\n- Cached card-detail opening target: **<200 ms**.\n- Design supports at least **200 lists/board**, **5,000 cards/board**, and **100,000 archived cards/organization**.\n- Log errors with correlation IDs but avoid logging sensitive content bodies by default.\n\n## 20. Analytics / Telemetry\nTrack:\n- feature open/use counts;\n- mutation latency and success/failure;\n- permission denials by stable error code;\n- realtime reconnect/conflict rates;\n- client exceptions;\n- user-visible retry events.\nDo not use analytics events as the source of truth for audit history.\n\n## 21. Dependencies\n- PRD-02\n- PRD-03\n- PRD-04\n- PRD-06\n- PRD-08\n- PRD-09\n\n## 22. Out of Scope\nFeature-specific behavior, integrations, billing, enterprise controls.\n\n## 23. Acceptance Criteria\n**AC-FOUND-01-01**\nGIVEN an authorized user is using this feature\nWHEN the user performs the primary supported action associated with FOUND-FR-001\nTHEN the server validates authorization and input\nAND the resulting state is persisted\nAND the client reflects the authoritative result.\n\n**AC-FOUND-01-02**\nGIVEN the same operation would violate the rule represented by FOUND-FR-003\nWHEN the user or client attempts the operation\nTHEN the server rejects it with a stable error code\nAND protected state is unchanged\nAND no unauthorized information is disclosed.\n\n**AC-FOUND-01-03**\nGIVEN two clients have the same board or entity open\nWHEN a successful mutation relevant to FOUND-FR-010 occurs\nTHEN the initiating client receives confirmation\nAND other authorized clients receive or recover the updated state without requiring a full manual reload.\n\n## 24.
