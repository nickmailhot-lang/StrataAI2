# List movement between Boards (PRD-07)

[PRD-07](https://github.com/nickmailhot-lang/StrataAI2/issues/8) includes moving a List to another authorized Board. Existing List reordering and copying do not satisfy that requirement. The implementation is in progress; this document preserves the full movement scope while recording the first Domain increment.

## Canonical Domain transition

`BoardList.MoveToBoard` changes the parent Board and normalized rank within the List's existing Organization. Identity, Organization, name and creation history remain unchanged; one successful transition advances its version and update timestamp once. Empty destinations, different/empty Organizations, empty ranks and backwards timestamps are rejected before changing the parent or rank. Caller-supplied destination context is not authorization: the Application service must resolve and admit both real Board scopes before invoking a transition.

Nine focused Domain cases cover identity/history preservation, subsequent movement and complete unchanged state for invalid scope, destination, rank and time. Together with the four existing canonical hierarchy cases, **13/13 pass**, zero skipped or failed. A fresh solution build succeeds with no warnings/errors; all 213 immutable CI coverage guards pass. These checks establish the entity transition, not a working transfer endpoint or full PRD acceptance.

## Domain rejection atomicity

The graph review found that `Card.Move` assigned parent IDs before rank validation, and canonical rename/reorder methods assigned fields before rejecting backwards timestamps. A rejected operation could therefore leave a partially changed in-memory entity. These methods now normalize input and complete clock validation before assigning their fields. Accepted values, normalization and successful version/time advancement remain unchanged.

Before the repair, nine of ten targeted rejection cases fail complete serialized-state comparisons; the new List-to-Board transition already passes its corresponding guard. After the repair, all rejection cases and seven successful mutation paths pass. Combined with List movement and canonical hierarchy coverage, **30/30 pass**, zero failed/skipped. The final solution build has no warnings/errors and all 217 CI coverage guards pass. This establishes Domain validation behavior; it does not prove transfer persistence, HTTP authorization or the whole graph transaction. The complete List-transfer implementation below remains necessary, with estimated PRD-07 work remaining unchanged at **35%**.

## Shared label reference planning

`CardLabelTransferPlan` captures source definitions and Card associations before mutation. Multiple Cards sharing a source label retain one planned definition and every distinct association. It rejects mismatched Organization/Board definitions, unknown Cards or labels, and conflicting versions of a definition. Deleted and unreferenced definitions do not become destination labels; source ordering uses ordinal rank. The plan owns an immutable snapshot and grants no destination authorization. ## Application command admission and replay

`ListBoardMovementCommand` wraps the admitted graph-transfer/publication operation in the existing Work unit of work. It captures the explicit original source, destination and current parent, acquires their command scopes in deterministic order, and requires current move rights, active Boards, an active Organization and a current actor session. Invalid or overflowing versions are refused before transfer. The original request fingerprint includes both Boards, version and destination anchor. Replay requires those original contexts and the current parent to remain admitted, even after another subsequent List movement.

After the callback, the command rechecks actor/session, Board rights and Organization lifecycle. A successful acknowledgment must exactly match the persisted List and its expected destination/version. Failed admission or a fabricated acknowledgment rolls back the transaction; no receipt is retained, allowing the original key to retry.

Nine actual Demo-unit checks pass with no failures/skips: seven command cases plus existing mixed-graph and canonical-binding rollback regressions. They cover late actor loss, source/destination archival, fabricated acknowledgment, unchanged List/Card/Board rollback, original-key retry/replay without repeated transfer, changed-input key refusal, original/destination/current-parent replay withdrawal, subsequent third-Board movement, and invalid/overflowing versions. Authorization uses the real Board resolver; actor/session loss is controlled by a fixture. A fresh solution build has zero warnings/errors and all 219 CI/startup guards pass. These memory-only tests create no Docker resources or duplicate runtimes.

The command is registered for both storage modes. The owning orchestration below now supplies its transfer/publication callback; the public endpoint and complete production acceptance remain pending. PostgreSQL Application-level admission/receipt/publication tests, downstream reconciliation, HTTP/MUI and retained-image acceptance remain required. Each contained Card lifecycle receives one `CARD_MOVED` audit fact and a distinct event in each Board stream; the List receives one `LIST_MOVED` audit fact and both stream events. The existing event stores retain their normal Demo activity projection and PostgreSQL transactional outbox/Worker delivery path. Current destination watch admission runs only through the existing producer. Reminder candidates are reconciled using the existing scheduler: eligible unchanged choices keep an already overdue queued attempt; destination-ineligible recipients and hidden Card lifecycles lose scheduling eligibility. Final command admission still controls commit and receipt retention.
