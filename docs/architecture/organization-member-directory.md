# Authorized Organization member directory

`GET /organizations/{id}/members?after={userId}` returns at most 50 current internal memberships, ordered by immutable user UUID, with a next-page cursor when a 51st row exists. Each page identifies its Organization. Empty or malformed cursors are rejected with a stable `invalid_member_cursor` problem. No total count or unrelated Organization metadata is returned.

Only a current internal Owner or Admin of an active Organization can read the directory. A separate Portal relationship does not grant access. The read enters the existing Organization unit of work: parent gate, current actor membership, active account and original session are frozen/rechecked after lock waits before protected disclosure. The restricted PostgreSQL store refuses calls without that owning authorized Organization transaction and borrows its connection; no additional connection, cross-tenant join, fabricated tenant or RLS bypass is introduced.

Returned fields are the membership ID, user ID, display name, email, internal role, account status, email-verification status, joined/updated timestamps and membership version. Password/token hashes and normalized-email internals are excluded. Only canonical active memberships are included; historical membership of an inactive account remains visible to administrators for governance context. `isUsableOwner` applies the same active-account and configured verification rule as deactivation/departure continuity, so historical Owner membership cannot be confused with a usable Owner. It is descriptive; every subsequent mutation reevaluates authorization and continuity on the server.

Pages are current authorized snapshots rather than a frozen export. Membership changes between pages can change the current directory; callers refresh when they need a fresh review. UUID pagination remains forward-only, bounded and tenant-scoped. Reads produce no audit mutation or domain event. Demo uses the shared process-local command gate and matching ordering/eligibility rules; it does not establish durable database isolation.

Local evidence includes a clean warnings-as-errors solution build and a real browser-context API scenario exercising unrelated-account denial, administrative admission through an accepted invitation, Portal separation, owner-protection denial, removal and immediate access revocation. New API host tests compile and cover 67-member contiguous paging, rejected cursors, demotion, protected scopes and inactive historical ownership. Their execution is required in Linux CI; the local Windows test runner has been blocked by Application Control.

The mandatory exact-image fixture uses the restricted runtime role with a one-connection pool, compares 68 returned user IDs with canonical scoped rows, checks field exclusion and lifecycle eligibility, and forces role demotion and original-session revocation during real lock waits. It also proves the read leaves audit history unchanged. These execution claims remain pending until the exact-head CI logs pass; Bash syntax and compilation alone are insufficient proof.

The [member administration screen](organization-member-administration.md) now consumes this contract and the authorized single-member review, including current actor-role metadata. Invitation-driven registration/delivery, role and ownership governance, durable retry receipts, Organization events, deletion/retention and the remaining PRD-03/60 acceptance are still open.
