# Account deactivation and active Organization owners

Self-deactivation refuses with `organization_owner_required` (409) if any owned Organization that has not begun deletion would lose its last usable Owner. An alternative must have active canonical internal OWNER membership and an ACTIVE global account; verified email is additionally required when that authentication policy is enabled. Admin membership and separate Owner Portal relationships do not satisfy internal ownership. Archived Organizations still require continuity. Membership and historical attribution remain stored after successful account deactivation.

Both unkeyed and keyed deactivation enter the existing global identity command transaction. Schema 021 guarantees complete, matching routing records. Routing supplies only a lock plan: the API sets each real Organization's transaction-local RLS scope, freezes parent rows in PostgreSQL UUID order and freezes the actor's membership before locking the account/session. It then clears the tenant setting. No fabricated tenant, nested transaction, privileged function or RLS bypass is introduced.

After account admission, the API rereads owned routes. A newly committed Owner grant outside the frozen plan produces `ownership_changed` (409), with no late Organization lock and no account mutation. Canonical active owners are reread under held parent/membership locks. Alternative owner accounts are frozen for share in global UUID order and their current status/verification is checked after waits. Current actor/session admission is repeated after these waits. Refusal includes no Organization names/IDs and preserves account, sessions, audits, event sequence/history and retry receipt. The browser cookie is deleted only on confirmed success.

On success, account deactivation, session revocation, audit, event and optional existing session-bound receipt commit together. A matching previously completed receipt remains an empty acknowledgment; it does not rerun continuity, repeat deactivation, remove historical membership or authorize any protected read. An unconfirmed refused key can be retried after ownership is repaired because no receipt was published.

Organization owner departure/removal now checks other active, usable Owner accounts rather than counting historical memberships of deactivated or suspended users. It freezes those account rows within the existing Organization transaction. Deactivation and departure share the parent gate, so concurrent operations preserve one usable Owner. Demo identity and Organization commands share one DI-owned process-local semaphore and apply the same status rule; this does not prove durable rollback or cross-process transactions.

Host tests cover keyed/unkeyed refusal, preserved state and retry keys, another Owner repairing continuity, every owned Organization, Admin/inactive-owner exclusion, acknowledgment-only replay and simultaneous deactivation/departure. The required exact-image CI fixture covers real restricted PostgreSQL commands, audit/event/receipt rollback, original-session revocation during a parent wait, newly committed ownership during an account wait, alternative-owner lifecycle change during a share wait, verified-email policy with a one-connection pool, historical membership/replay, and forced concurrent departures. The existing Demo release lifecycle fixture repairs ownership through real internal OWNER invitations before deactivation.

Execution evidence remains in CI; a clean build alone is insufficient proof. The deactivation confirmation/recovery UI, broader ownership administration/transfer, Organization events, lifecycle processing, telemetry and remaining PRD acceptance are still open. This increment does not close PRD-02/03 or architecture issues.
