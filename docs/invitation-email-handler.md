# Invitation email handler and protected delivery contract

The application handler uses the existing tenant background-job processor and mail transport. Its job type is `INVITATION_EMAIL`, service identity `invitation-email-delivery`, and metadata contains exactly one nonempty `invitationId`. Recipient, token hash, key version and mail snapshot belong in the protected delivery store, never generic job metadata.

The store contract requires admission of the live Organization/job/worker/lease/service claim, current canonical invitation/recipient/issuer/grant/lifecycle/expiry and immutable mail snapshot. It must close its short transaction before provider work. The handler also checks envelope scope and creator, supported surface/role/template, plain sender/recipient, HTTPS origin, provider-account continuity and constant-time canonical hash agreement with reconstructed proof.

Template version 1 uses a generic subject/body and `/invitation#token=...`; Organization names/roles are reviewed on the authorized screen. Original snapshot fields and the stable `strataai-invitation/{organization}/{invitation}` provider key keep repeated sends identical across leases and deployments. Expired/unusable invitations cancel, terminal ledger states do not send again, permanent provider errors persist only a constant safe code, and unknown/transient outcomes use bounded generic queue retries without storing provider exception text. Provider execution is bounded by the smaller remaining invitation/lease budget, including transports that ignore cancellation. Empty receipts cannot acknowledge delivery.

Delivery `Sent` is persisted under the same current lease before generic job completion. A crash afterward can complete the job without sending again. A lost ledger acknowledgment may send the same message/key again; provider idempotency protects that gap. Generic job completion means the delivery was handled, including cancellation/failure; it must not be displayed as successful email delivery without a `Sent` ledger acknowledgment. Delivery or acknowledgment never grants recipient access.
