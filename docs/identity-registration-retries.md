# Registration retries

`POST /auth/register` accepts an optional nonempty UUID `Idempotency-Key`. Registration policy and input validation still apply. A duplicate must prove the current account password and an active or pending-verification lifecycle before reading a receipt. Its normalized email, password, display name, locale and timezone must match the original keyed intent. A different key for an existing email cannot acknowledge account creation.

The user, verification token, delivery job, audit, identity event and typed receipt share the identity command transaction. Concurrent first inserts resolve through the unique normalized email and reread the committed winner under the user lock. Receipts contain a keyed fingerprint, key versions and the original verification-token identifier; they contain no password, bearer, response JSON or cached profile. A retry returns the current authorized profile. It creates no session and sends no additional email.

Registration uses the existing API-only `STRATAAI_AUTH_RETRY_CURRENT_KEY` and `STRATAAI_AUTH_RETRY_KEYS` ring, with distinct registration intent and verification derivation purposes. Retain versions needed by live receipts when rotating. Production email verification retains its original delivery signing-key version as well. A removed required version fails closed with `identity_retry_key_unavailable`. An unverified account requires the original verification proof to remain valid; an expired or revoked proof returns `idempotency_key_expired`. A verified account returns no verification token. Production responses never expose the email bearer.

Migration 018 forces subject RLS and a same-user verification-token foreign key. API receipt grants allow insert/read but no update/delete. The Worker can read only identifiers and expiry for expired cleanup receipts, cannot read fingerprints or key versions, and deletes at most 100 registration receipts per cleanup transaction. Together with profile, revocation and sign-in cleanup, the existing pass is bounded to 400 rows. Cleanup preserves account, token, audit and event history. After receipt deletion, an existing account still cannot be recreated by reusing its key.

The MUI form retains the same UUID, mode and submitted details after a lost or invalid acknowledgment, including the password until a valid creation acknowledgment. It validates the returned identity and email before clearing the password and showing the sign-in form. Its existing transport/body deadline and unmount cancellation apply. An expired registration proof directs the user to resend verification.

Required release fixtures cover restricted roles, rollback at each publication boundary, concurrent inserts, retained/retired API keys, restart, lifecycle denial, Worker cleanup, and production verification delivery.
