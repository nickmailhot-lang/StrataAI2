# UX-004: Actionable Dashboard and Personalized Work Queues

Status: Specified; no second dashboard or new domain model.

## Scope and ownership

Incremental UX delivery workstream. Canonical business/security requirements remain in PRD-54/55 (business owners); PRD-11/12/17/58/67/72/77. This PRD adds implementation and acceptance detail; it does not replace or close those tickets. No new database schema, API contract, tenant permission or parallel frontend framework is authorized by this PRD.

## Dependencies

UX-001/002/003; authorized authoritative source queries owned by existing feature PRDs. Source availability gates widgets, not unrelated feature delivery.

## User journeys

Contributor opens overdue/assigned work and continues the source Card; Council member finds review items; President/Manager sees eligible emphasis; user changes role or Organization and sees only current authorized work.

## Implementation tasks

- [ ] UX-004-T-01: Apply shared page/action slots to PRD-54/55 implementation, documenting widget priority and empty/loading/error/stale states.
- [ ] UX-004-T-02: Link each widget to a filtered source with recoverable return context; avoid duplicate workflow storage and duplicate counts.
- [ ] UX-004-T-03: Use allowed widget ordering/visibility and role emphasis from PRD-55; explicitly mark unavailable source integrations.
- [ ] UX-004-T-04: Preserve source authorization before aggregation, confidentiality and portfolio boundaries.

## Acceptance criteria

- UX-004-AC-01: Each actionable widget has a working authorized source deep link and clear next action; no decorative-only MVP widget.
- UX-004-AC-02: Counts/content are filtered before disclosure, including live role loss and cross-Organization switching.
- UX-004-AC-03: Loading, empty, partial failure and last-refreshed state are distinguishable and accessible.
- UX-004-AC-04: Personalization does not grant access or duplicate counts; PRD-54/55 own dashboard functionality and persistence.

## Automated tests

- UX-004-TC-01: Unit: widget eligibility, priority, deduplication, loading/empty/stale/partial error rendering.
- UX-004-TC-02: Integration: real filtered counts and source links under role/confidentiality matrix; no hidden-record existence leaks.
- UX-004-TC-03: Playwright: open queue → filtered source → complete permitted work → return/refresh at four widths, keyboard/Axe; restricted and Portal identities.

## Delivery and acceptance

Use the [shared feature UX acceptance addendum](feature-acceptance.md) and [single delivery report](delivery-report.md). Record implemented, tested and accepted separately. Tests above are required coverage, not a claim of execution. Existing feature delivery can proceed where it does not mutate shared shell/navigation/theme files. One owner edits those files in each integration window; feature owners consume approved slots. Use a small PR per migration; use a reversible feature flag before any migration that would interrupt an existing workflow. This additive specification does not flag or replace working business functionality.

Acceptance requires all applicable quality gates, current revision evidence, documented failure evaluation and role-specific end-to-end review. UX completion cannot raise functional completion or MVP readiness by itself.
