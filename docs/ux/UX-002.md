# UX-002: Information Architecture and Role-Based Menus

Status: Specified; no new capability or menu policy implemented.

## Scope and ownership

Incremental UX delivery workstream. Canonical business/security requirements remain in PRD-01; PRD-03/05/24/29/31/32/35/67/80; ARCH-06. This PRD adds implementation and acceptance detail; it does not replace or close those tickets. No new database schema, API contract, tenant permission or parallel frontend framework is authorized by this PRD.

## Dependencies

UX-001 shared shell slots; reuse existing server surface/capability contracts. Do not invent roles, permission endpoints or infer permission from labels.

The [existing route/discovery inventory](route-inventory.md) is an initial source audit. Capability consolidation and live role-menu behavior remain unimplemented.

## User journeys

Owner/Admin finds Organization administration; Board Admin reaches Board settings; Contributor reaches assigned work; Viewer reads permitted Boards; President/Manager perspectives use granted acting capacity; Portal identity sees only published portal journeys.

## Implementation tasks

- [ ] UX-002-T-01: Build a route-to-capability inventory including deep-link fallback, global/account, Organization, Board and Portal contexts.
- [ ] UX-002-T-02: Define canonical labels and group ordering with a menu entry contract: stable destination, surface, current section, required capability, empty/denied state.
- [ ] UX-002-T-03: Resolve capabilities from existing authoritative responses; hide unauthorized items and show unavailable modules without clickable dead ends.
- [ ] UX-002-T-04: Handle role/session/Organization changes, retire old context immediately, and document future module slots without introducing routes.

## Acceptance criteria

- UX-002-AC-01: Every implemented route has a documented discovery entry and return path; future modules have no misleading active destination.
- UX-002-AC-02: Menus reflect current authoritative scope; multi-role users receive one coherent menu with no duplicate entries or counts.
- UX-002-AC-03: Organization switching, role loss, Portal-only access and stale capability responses cannot expose protected names, counts or actions.
- UX-002-AC-04: UI visibility never grants access; direct URL/API refusal and public Board exceptions preserve existing contracts.

## Automated tests

- UX-002-TC-01: Unit: table-driven role/surface/capability-to-menu rules, active routes and stale-scope rejection.
- UX-002-TC-02: Integration: real Owner/Admin, Board Admin, Contributor, Viewer, Portal-only and nonmember HTTP checks; no cross-tenant disclosure.
- UX-002-TC-03: Playwright: keyboard discovery/return at all four widths, live role loss with drawer open, multi-role switching, direct denied URLs and Axe.

## Delivery and acceptance

Use the [shared feature UX acceptance addendum](feature-acceptance.md) and [single delivery report](delivery-report.md). Record implemented, tested and accepted separately. Tests above are required coverage, not a claim of execution. Existing feature delivery can proceed where it does not mutate shared shell/navigation/theme files. One owner edits those files in each integration window; feature owners consume approved slots. Use a small PR per migration; use a reversible feature flag before any migration that would interrupt an existing workflow. This additive specification does not flag or replace working business functionality.

Acceptance requires all applicable quality gates, current revision evidence, documented failure evaluation and role-specific end-to-end review. UX completion cannot raise functional completion or MVP readiness by itself.
